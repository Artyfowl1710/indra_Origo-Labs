# Security model and safe operation

## Trust boundaries

Indra Origo is a local, single-user workstation harness—not a hardened multi-user server. It binds to `127.0.0.1` by default and rejects obvious foreign Host/Origin and cross-site browser requests. These checks are defense in depth, not authentication. Any local process running as the same Windows user may still be able to access local endpoints or files.

- Do not bind to `0.0.0.0`, forward the port, or expose it on a LAN. The supported remote path is private Tailscale Serve HTTPS with the opt-in flag plus a 256-bit token generated by `enable_remote_tailscale.ps1`; remote routes use a host-bound signed cookie that expires after 12 hours. Keep tailnet ACLs restricted as well. This remains a single-user system, not a hardened multi-user server.
- Keep `.env`, `data/`, `logs/`, backups and exports private. Run history can contain prompts, tool arguments and file excerpts. Review exports before sharing.
- The configured model endpoint receives prompts and context sent to it. A local URL is suitable for local inference; hosted endpoints may receive project information.
- A model, fetched page, skill, plugin description, child-agent result or tool result is not a policy authority. It is untrusted data. The harness applies the trusted tool registry, argument checks and budgets.

## File and action policy

- File tools remain inside the selected workspace, reject traversal and link-like paths, prune common dependency/build directories, and block common secret filenames/directories and key/certificate suffixes.
- Only an allowlist of text-like file types is read, with configured size limits. Common token formats and credential assignments are best-effort redacted. This is not a substitute for a real secret scanner.
- Proposed changes are not written until a human approves them. Approvals record target existence and a content hash, reject stale changes, create/verify overwrite backups, stage content beside the target and recheck before replacement.
- Undo refuses to overwrite later user edits. A filesystem change by another process can still race between checks and replacement.
- **Host-shell execution and desktop control are not available.** The optional command runner requires Docker Desktop, an explicitly enabled setting and a pre-pulled local image. It uses a disposable sanitized text-only snapshot, does not bind-mount the host workspace, disables networking, uses a read-only root filesystem with bounded temporary filesystems, drops Linux capabilities, runs user commands as a non-root UID and applies memory/CPU/PID/time/output limits. No output is automatically written back.
- Docker is still part of the trusted computing base. Docker Desktop/WSL2, the image and the host kernel must be kept updated. A container is not a guarantee against every kernel/daemon vulnerability. The sandbox has not been tested here against a running Docker daemon.
- The **Build dev image** action is a host-side Docker build, not a sandboxed action. It is gated by a confirmation modal and its build context is restricted to the project `docker/` folder, excluding workspace files, `.env` and local runtime data. Docker still downloads the declared base image and packages from configured registries; review the Dockerfile and trust those registries before accepting.
- The selected development image override is stored in the local SQLite settings database. **Use .env image** clears the override; it does not change `.env`. An image-build success only verifies that Docker returned success, not that every project command works inside the container.

## Web extraction and SSRF

- Web tools are explicit, user-initiated, HTTPS-first, use no environment proxy, restrict ports, cap bodies/text/pages/time, rate-limit per host, revalidate redirects, respect `robots.txt` by default, and can enforce `INDRA_WEB_ALLOWED_DOMAINS`.
- Robots policy is cached as a parsed per-origin policy and evaluated for each URL path; the cached decision is not reused indiscriminately for all paths.
- Web content is source material, never instructions. The extractor is static HTML/text/JSON; it does not run site JavaScript or bypass login, paywalls or CAPTCHAs.
- URL DNS/IP validation is only a mitigation, not a complete SSRF boundary: DNS is resolved separately from the socket connection, leaving rebinding/TOCTOU risk. A high-assurance deployment needs OS/container outbound egress controls and, for strict allowlisting, an outbound proxy/firewall. Do not assume URL validation alone can protect a sensitive host.

## Skills and plugins

- Skills are Markdown `SKILL.md` files. They are loaded as bounded reference guidance; no skill Python, JavaScript or shell is executed. Review any custom skill before selecting it.
- Plugins are declarative JSON manifests calling HTTP JSON endpoints on an explicitly configured numeric loopback IP. The app does not import third-party code into the host process. Plugins need both a manifest `enabled: true` flag and `INDRA_ENABLE_LOCAL_HTTP_PLUGINS=true`.
- Model-visible plugin tools must declare `read_only: true`, but this is only a contract assertion. HTTP `POST` can have side effects. Only configure a local service you trust; the registry cannot prove that a plugin endpoint is actually read-only. Mutating tool support is not exposed because it needs a separate human-approval capability.
- Plugin responses are capped and schemas are restricted. The local plugin service still runs with its own process permissions and is outside Indra's sandbox.
- Dependency-aware and independent child-agent tasks are bounded by node count, concurrency and run time. Children have read-only workspace tools, no plugins, no sandbox command execution and no recursive delegation. Child outputs are untrusted evidence. The model server may receive multiple concurrent requests, so set `INDRA_MAX_ACTIVE_CHILDREN=1` on slow or memory-constrained local setups.

## Retrieval and local services

- Optional Qdrant retrieval is disabled by default. When enabled it reads one configured collection and never indexes/upserts/deletes points. Retrieval results are untrusted data.
- Workbench integration reports metadata/schema only. No discovered business endpoint is invoked automatically.
- Configure local service endpoints deliberately. Read-only status checks are still network requests.

## Operational hardening

- Windows scripts bind only to loopback, log startup failures and check the app identity/version before declaring startup complete. Remote sign-in is fail-closed when the token is absent/too short. Rotating or clearing the token revokes existing remote session cookies. Remote responses are marked no-store and HTTPS remote responses add host-only HSTS. Use the in-app Sign out control when finished on a shared/borrowed device. The `.env` file contains a bearer secret and must remain private.
- Setup runs Python compilation, the offline regression suite and a frontend syntax check if Node.js is installed. That does not substitute for running the launch scripts on real Windows or testing your live model/server.
- SQLite WAL is intended for local, same-host storage. Do not put `INDRA_DATA_DIR` on a network share.
